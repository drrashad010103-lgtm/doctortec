# خطة ترحيل البيانات — من PHP القديم إلى VB.NET

**الحالة:** الخطة مكتوبة من **الكود المنفّذ** (`RsSales.DbTool import-legacy`) ومن
جرد المصدر في `docs/DATABASE_SCHEMA.md`. سكربت الاستيراد **جزئي**: يستورد
الأصناف والباركودات والعملاء والمجموعات والوحدات واسم الشركة فقط.
**آخر تحديث:** 2026-10-30
**آخر تجربة:** 2026-10-30 — استيراد **1,000 صنف** ثم **الترحيل الكامل
(29,576 صنفًا)** من `rs_pharmacy_test` إلى قواعد مؤقتة، مع `verify` ناجح
(النتائج في §11).
**مرتبط بـ:** D-04 (لا استيراد فواتير)، D-11 (نموذج الفروع)،
`docs/PHASE_0_INVENTORY.md` (بصمات النسخ)، `docs/TAX_DESIGN.md` §11.

> ⚠️ **قاعدة غير قابلة للتفاوض:** المصدر `D:\rs_pharmacy` **للقراءة فقط**.
> الاستيراد يقرأ منه ويكتب **فقط** في قاعدة الهدف. لا يكتب حرفًا في المصدر ولا
> في قاعدة الإنتاج `rs_pharmacy`.

## 1. المبادئ

1. **لا نسخ جداول**: كل جدول في الهدف يُبنى من هجرات `V001__init.sql`، ثم تُنقل
   البيانات انتقائيًا.
2. **المخزون لا يُنسخ**: `stock_balances` تُبنى من الحركات. الرصيد الافتتاحي
   يُدخل كوثيقة `opening` (D-04)، لا كأرقام مباشرة.
3. **لا فواتير تاريخية**: قرار D-04. النظام القديم فيه 0 فاتورة أصلًا، فالقرار
   بلا تكلفة.
4. **التحقق قبل النقل وقبله**: بصمات SHA-256 للنسخ، وعدّادات صفوف، وتقرير
   تكرارات، ثم `verify` بعد النقل.
5. **إعادة التشغيل الآمنة** مطلوبة، وغير متحققة بالكامل حاليًا (انظر §8).

## 7. فحوص ما بعد الترحيل

### 7.1 ما تفحصه أداة `verify` تلقائيًا

| الفحص | المعيار |
|---|---|
| مطابقة المخزون | `qty_on_hand` = مجموع `qty_delta` لكل (فرع، صنف) — فرق > 0.00005 فشل |
| توازن القيود | كل قيد: `SUM(debit) = SUM(credit)` — فرق > 0.004 فشل |
| مطابقة الفاتورة | `invoices.tax_total` = مجموع ضرائب بنودها، و`total` = مجموع البنود |
| أرصدة سالبة | لا يوجد `qty_on_hand < 0` |
| فاتورة بلا حركة مخزون | لا توجد فاتورة مرحّلة (غير `adjustment`) بلا `stock_moves` |
| حالة الـ outbox | طباعة عدد المعلّق والميت |

تُرجع `VERIFY OK` أو فشلًا بـ`ExitCode=2` مع أول 50 مشكلة.

### 7.2 فحوص يدوية إضافية

| # | الفحص | المتوقع |
|---|---|---|
| 1 | `SELECT COUNT(*) FROM items` | = عدد الأصناف غير المحذوفة في المصدر |
| 2 | `SELECT COUNT(*) FROM item_barcodes` | ≤ عدد باركودات المصدر (بسبب التكرارات واليتامى) |
| 3 | `SELECT COUNT(*) FROM item_barcodes WHERE LENGTH(barcode)<8` | مراجعة يدوية للباركودات القصيرة المشكوك فيها |
| 4 | `SELECT COUNT(*) FROM customers` | = غير المحذوف وبلا اسم |
| 5 | `SELECT COUNT(*) FROM items WHERE tax_category_id=(SELECT id FROM tax_categories WHERE code='vat14')` | صفر قبل قرار الضريبة |
| 6 | `SELECT COUNT(*) FROM stock_balances` | صفر قبل إدخال المخزون الأول |
| 7 | عيّنة 20 صنفًا: مقارنة الأسعار والاسم والباركود مع المصدر | مطابقة تامة |
| 8 | بحث/مسح 10 باركودات في شاشة البيع | يعمل |
| 9 | `site: v_stock` | يظهر كل صنف مفعّل حتى بلا صف رصيد (سلوك مقصود: الرصيد 0) |

## 8. الثغرات المعروفة في سكربت الاستيراد

| # | الثغرة | الأثر | الإصلاح المقترح |
|---|---|---|---|
| M-1 | **العملاء يُدرجون دائمًا** بلا `ON DUPLICATE` وبلا مفتاح مصدر | إعادة تشغيل الاستيراد **تُضاعف العملاء** | إضافة عمود `legacy_id` أو مطابقة بـ`(mobile, tax_no)` ثم `INSERT IGNORE` |
| M-2 | تكرار باركود بين صنفين ⇒ **آخر صنف يفوز صامتًا** | صنف يفقد باركوده بلا إنذار | تقرير تعارضات + تخطّي أو تحويل إلى صنف مساعد |
| M-3 | شجرة المجموعات **تُسطَّح** (`parent_id=NULL`) | فقدان التسلسل الهرمي | نقل `parent_id` بعد التحقق من عدم وجود دورات |
| M-4 | كل العملاء بنوع `customer` | الموردون يفقدون وصفهم | تحويل نوع المورد من `currencies.ref_vendor` / `cust_groups` أو جدول الموردين |
| M-5 | كل الأصناف `vat0` | تشغيل الضريبة يحتاج مراجعة يدوية للتصنيفات | استيراد `tax_group` إن صلح للمعنى الجديد |
| M-6 | حفظ `id` القديم في `items` يعني احتمال تصادم مع أصناف جديدة | لو أضيف صنف جديد إلى الهدف قبل الترحيل ⇒ استبداله | ربط `legacy_id` منفصل بدل استخدام `id` |
| M-7 | لا استيراد رقم ضريبي للشركة ولا عنوان/هاتف | الفاتورة الضريبية تنقص بيانات | توسيع خطوة الهوية لتقرأ `tax_no`, `Address`, `Tel`, `Mobile` |
| M-8 | شجرة الحسابات تُستبدل بـ13 حسابًا فقط | لا مطابقة مع 177 حسابًا قديمة | خطة تحويل صريحة أو إبقاء الشجرة المبسّطة بقرار مالك |
| M-9 | لا تحقق من عدد الصفوف المتوقع | قد ينتهي الاستيراد "ناجحًا" بنقل ناقص | طباعة/مقارنة الأعداد مقابل العدّادات المرجعية |
| M-10 | الاستيراد كله في معاملة واحدة لـ29,595 صنفًا | معاملة طويلة وقد تنتهي بمهلة | دفعات كل 1,000 داخل معاملة، مع `--limit` و`--offset` |
| M-11 | لا يسجّل في `audit_log` ولا `change_log` | لا أثر تدقيقي للترحيل | تسجيل حدث `legacy_import` |
| M-12 | الأصناف غير المزامَنة مع المركز (لا تُضاف إلى outbox) | المركز لا يعرف بالمخزون الأساسي إلا بتدفق آخر | راجع `SYNC_PROTOCOL.md` §4 |
| M-13 | ✅ **أُصلح:** `currencies.unit` و`` `limit` `` لا يُسندان إلى `UnitId`/`ReorderLevel` | كان `base_unit_id=NULL` لكل الأصناف، و`reorder_level` يفقد أي قيمة | `unit AS UnitId` و`` `limit` AS ReorderLevel ``؛ تحقق منه الترحيل الكامل |
| M-14 | ✅ **أُصلح:** `PostOpeningStock` يُدرج رأس الفاتورة بأصفار ولا يحدّثها بعد بناء الأسطر | `invoices.total=0` بينما الأسطر 27,109.70 ⇒ `verify` يفشل، وتقارير الفواتير تعرض صفرًا | `InvoicesRepository.UpdateTotals` بعد الحلقة + تحقق من الرأس في اختبار المخزون الأول |
| M-15 | ✅ **أُصلح:** حركة البيع تُسجّل `unit_cost=0` بينما السطر والقيد يستخدمان التكلفة الفعلية | قيمة المخزون المحسوبة من `stock_moves` تنقص بمقدار تكلفة المبيعات (408 في الدورة) وتخالف حساب المخزون | تمرير `costExcl` إلى `AddMove` + تحقق من `unit_cost` في اختبار البيع |

## 9. المخزون الافتتاحي (المسار البديل عن النسخ)

قرار D-04: الرصيد الافتتاحي = **وثيقة جديدة**، لا أرقام منسوخة.

| الخطوة | التفصيل |
|---|---|
| 1 | حصر الأصناف ذات رصيد فعلي في المصدر (`item_bal` / `stock`) |
| 2 | تحديد **التكلفة الافتتاحية**: آخر `purch_price` أو تكلفة مراجعة يدويًا |
| 3 | إدخال وثيقة `opening` عبر `PurchaseService.PostOpeningStock` (تحتاج صلاحية `stock.opening`) |
| 4 | التحقق: `stock_balances` = مجموع الحركات، وقيود المخزون مقابل رأس المال متوازنة |
| 5 | مطابقة الإجمالي: قيمة المخزون الافتتاحي = مجموع (كمية × تكلفة) |

**لماذا لا نسخ مباشر؟** لأن `stock_balances` مخزن مؤقت؛ نسخه بلا حركات يجعل
`verify` يفشل، ويكسر التقارير ومصدر الحقيقة.

## 10. القطع والرجوع (Cutover & Rollback)

### 10.1 سيناريو القطع (المرحلة 7)

1. تجميد البيع في النظام القديم (وقت إغلاق معلن).
2. نسخة نهائية + بصمة SHA-256.
3. ترحيل إلى قاعدة الفرع الجديدة + إدخال المخزون الأول + مستخدمين وأدوار.
4. `verify` + `status` + فحوص §7.2.
5. تسليم 3–5 أصناف مرجعية ومطابقتها يدويًا (أسعار، باركود، رصيد).
6. تشغيل متوازٍ: النظام الجديد للبيع، والقديم للقراءة فقط لمراجعة الأرقام.
7. توقيع المالك ⇒ إيقاف القديم.

### 10.2 الرجوع

| الحالة | الإجراء |
|---|---|
| فشل أثناء الاستيراد | المعاملة تتراجع تلقائيًا؛ الهدف يبقى نظيفًا بعد `migrate` |
| أخطاء اكتُشفت بعد الترحيل | إسقاط قاعدة الهدف وإعادة التنفيذ من النسخة (لا توجد بيانات تشغيلية بعد) |
| خلل بعد بدء التشغيل | استرجاع القديم للعمل (لم يُوقف إلا بالتوقيع) + إعادة تشغيل الهدف من نسخة |
| فشل هجرة المخطط | `db/rollback/R001__init.sql` عبر `DbTool rollback` (مُختبَر: انظر §11) |

**مبدأ:** لا يُحذف الأصل ولا تُلمس قاعدة الإنتاج قبل توقيع المالك.
